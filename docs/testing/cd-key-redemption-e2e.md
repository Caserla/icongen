# CD-Key 充值真实交互测试用例

更新时间：2026-09-03

## CASE-CREDIT-001：有效 CD-Key 仅可到账一次

目标：验证用户通过点数记录页兑换 CD-Key 后，余额与充值流水同步增加；同一兑换码不能重复到账。

前置条件：

- 测试账户已登录、邮箱已验证且账户状态正常。
- Supabase 已执行 `0016_cd_key_ledger_entry_type.sql` 与 `0017_cd_key_redemption.sql`。
- 使用 Service Role 创建一枚 1 点、未过期、未停用的测试 CD-Key，内部备注为 `CASE-CREDIT-001`。

步骤与预期：

1. 从“个人信息”的点数卡片进入“点数记录”。预期页面显示当前余额、CD-Key 输入框以及“全部 / 消耗记录 / 充值记录”。
2. 记录兑换前余额 `B`，输入有效测试 CD-Key，点击“立即兑换”。预期按钮进入“兑换中…”状态，且不能重复提交。
3. 等待接口完成。预期显示“兑换成功，已到账 1 点”，余额变为 `B + 1`。
4. 查看“全部”。预期首条出现“CD-Key 充值”、金额 `+1`、变动后余额 `B + 1`，且没有展示完整兑换码。
5. 切换“充值记录”。预期该笔 CD-Key 流水仍可见；切换“消耗记录”时该笔流水不可见。
6. 再次输入同一枚 CD-Key 并提交。预期提示“这个 CD-Key 已被使用”，余额不变且不新增第二条流水。
7. 刷新页面。预期余额与流水保持一致，证明结果已持久化而非仅前端临时状态。

通过标准：以上预期全部满足；同一兑换码在数据库中只有一次核销记录和一条 `cd_key_redemption` 账本记录。

数据说明：本用例会给当前测试账户永久增加 1 点。测试流水属于不可变审计数据，不做删除或回滚。

## 2026-09-03 实测结果

结论：通过。

- 当前登录账户兑换前余额为 28、流水 23 条。
- 测试码首次兑换成功，页面余额更新为 29、流水更新为 24 条。
- “充值记录”展示 `CD-Key 充值 / +1 / 余额 29`，仅显示末四位 `D7BA`，未泄露完整兑换码。
- “消耗记录”未混入该笔充值流水。
- 第二次提交同一测试码，页面提示“这个 CD-Key 已被使用”，余额未再次增加。
- 刷新页面后余额 29 和该笔流水仍然存在。
- 数据库复核：测试码只有一条核销记录，并且仅关联一条 `cd_key_redemption` 账本；账本金额为 `+1`，`balance_after` 为 29。
