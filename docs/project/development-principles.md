# 项目开发准则：UI 交互响应优先

## 核心原则

所有功能实现和研发设计方案都必须遵循“UI 交互响应优先”：用户发出操作后，界面先用可理解的状态变化确认操作，再由后台完成网络请求、持久化、生成或计算。用户不应通过等待、重复点击或刷新页面来确认操作是否生效。

该原则适用于前端、接口、数据模型、异步任务和测试设计，不只是视觉层要求。

## 交互时序

1. **即时确认**：点击、键盘或手势发生后立即更新按钮、弹窗、选择态、占位、进度或局部内容。
2. **后台执行**：耗时请求与持久化异步进行，避免阻塞其他无冲突的页面操作。
3. **局部收敛**：成功后仅同步受影响的数据，并保持用户当前的缩放、平移、滚动、选择和输入上下文。
4. **失败补偿**：失败后回滚乐观状态或展示可恢复的失败状态，说明失败原因并提供重试路径。

## 方案设计要求

- 在方案中明确操作属于乐观更新、处理中反馈还是必须等待确认，并写清选择原因。
- 可回滚且低风险的收藏、恢复、排序、移动、开关等操作，默认采用乐观 UI。
- 删除、付费、权限变更等高风险操作不得为了“快”而牺牲确认、鉴权和一致性，但点击后仍需即时显示受理或处理中状态。
- 后台接口应支持幂等、防重复提交和竞态处理；前端不得通过整页刷新掩盖状态同步问题。
- 恢复或新增画布对象时应保留其持久化位置，并用连续动画引导视角定位，避免瞬移和上下文丢失。
- 长任务应按已知数量展示对应占位；数量未知时不伪造数量，待解析后再建立占位。
- 弹窗关闭、项目切换、任务取消等交互要区分“UI 已响应”和“后台已完成”，必要时允许后台任务继续并在完成后局部同步。

## 验收清单

- 操作后是否立即出现明确反馈？
- 慢网环境下是否仍可理解当前状态，并防止重复提交？
- 成功后是否只更新局部内容，而非刷新整个页面？
- 失败后是否回滚一致、提示清楚且可以重试？
- 连续快速操作、响应乱序和接口重复调用是否安全？
- 是否保留滚动、画布视角、选择态、输入和焦点？
- 动效是否不阻塞鼠标、键盘与触控板操作，并兼容减少动态效果设置？
- 深色与浅色主题下，各状态是否都清楚可辨？

未满足上述要求的功能，不视为交互闭环完成。
