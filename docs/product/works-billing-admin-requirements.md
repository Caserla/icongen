# 作品、支付与运营业务模块需求

文档版本：2.0
产品阶段：MVP


## 1. 作品与下载模块

### 1.1 模块目标

让用户在离开生成页后仍能按用途、风格/结构和状态找到批量任务，查看每个主体的 3 个方案，并下载选中方案的原图与尺寸资产。

### WORK-001 我的图标列表 `/icons` — P0

列表以“生成任务”而不是单张图片为单位。每张任务卡展示：

- 任务名称或首个主体名称与“等 N 项”。
- 创建时间与最多 3 张真实方案缩略图；不足 3 张时保持相同缩略图尺寸。
- `queued / processing / completed / partial / failed` 状态。
- 查看结果入口。

一级按 App 交互图标/App 插画图标分类，二级按风格或线性/面性分类，三级按状态筛选；切换上级分类会重置不兼容下级条件。列表按当前筛选分页，首次无作品显示创建 CTA。

验收标准：刷新后状态准确；同一用户只能看到自己的任务；100 条以上任务采用游标分页而非一次加载。

### WORK-002 任务详情与选择恢复 `/icons/[jobId]` — P0

- 复用图片生成模块的阶段二页面。
- 显示提交时的主体、颜色、背景、用途、风格/结构、尺寸和版本摘要。
- 选择状态保存在当前结果页，用于批量 ZIP 下载。
- 用户可复制当前任务为新草稿；复制使用当前仍有效的核心设置映射，失效选项需重新确认。
- 已删除或过期资产显示明确状态，不展示损坏图片。

### WORK-004 ZIP 归档 — P0

请求体只接受当前任务的 `resultIds` 和允许尺寸；服务端去重并验证。归档异步超过 2 秒时返回 archive ID，前端显示进度并查询状态。

ZIP 包含：

- 按主体目录组织的 PNG。
- `manifest.json`：主体、variant、尺寸、颜色/背景、核心设置/Skill/模型版本和生成时间。
- 不包含 API Key、内部完整 Prompt、用户邮箱或账单信息。

### WORK-005 删除与保留 — P0

当前阶段不实现作品 30 天自动清理，也不要求历史列表和任务详情展示 30 天到期时间。作品保留期限与后续清理策略待产品重新立项后确定。


用户主动删除单个任务不在当前范围；账本和审计数据的保留与匿名化规则另行确认。

### 1.2 API 与异常

| 方法     | 路径                                     | 用途                         |
| -------- | ---------------------------------------- | ---------------------------- |
| `GET`    | `/api/generation/jobs`                   | 筛选和分页查询自己的任务     |
| `GET`    | `/api/generation/jobs/{jobId}`           | 查询详情、进度和结果         |
| `POST`   | `/api/generation/jobs/{jobId}/downloads` | 创建选中结果 ZIP             |
| `DELETE` | `/api/generation/jobs/{jobId}`           | P1 删除作品记录              |
| `POST`   | `/api/account/data-export`               | 删除宽限期内创建用户资产归档 |
| `GET`    | `/api/account/data-export/{exportId}`    | 查询导出状态和短时下载链接   |

核心错误：`AUTH_REQUIRED`、`RESOURCE_FORBIDDEN`、`RESULT_NOT_READY`、`NO_RESULTS_SELECTED`、`ARCHIVE_FAILED`、`ASSET_EXPIRED`。

### 1.3 指标与完成定义

指标：历史页回访率、详情打开率、筛选使用率、方案选择率和 ZIP 下载成功率。

完成定义：列表、详情、选择和 ZIP 下载均接入真实私有资源；刷新与跨设备状态符合规则；越权测试通过。

## 2. 点数与充值模块

### 2.1 模块目标


### BILL-001 点数包与价格 `/pricing` — P0

> 以下美元套餐是早期测试基线，不能直接作为正式上线价格。当前经营测算、人民币套餐建议及定版条件见 [AI 生成成本与点数套餐策略](./ai-cost-and-pricing-strategy.md)；在真实 Image2 `usage` 样本完成校准前，价格保持待确认。

首发测试点数包：

| 点数包  | USD 价格 | 点数 | 可生成主体数 | 定位     |
| ------- | -------: | ---: | -----------: | -------- |
| Starter |  `$2.99` |   30 |           30 | 轻量试用 |
| Maker   |  `$6.49` |   75 |           75 | 默认推荐 |
| Studio  | `$12.99` |  180 |          180 | 批量生产 |

页面展示 USD 价格、点数、推荐标记和按当前价格版本估算的“可生成图标主体数”。每个主体固定包含 3 个方案，整体消耗 1 点，不按单个方案拆分收费。


### BILL-001A 新用户体验点数 — P0

- 新用户获得一次 6 点体验点数，可生成 6 个主体、共 18 个方案。
- 新用户赠送点数永久有效，MVP 不设置领取后到期时间。
- 发放必须与账户初始化事务一致并使用稳定业务键保证幂等。
- 后台可查询发放记录和执行失败补偿，但不能再次手工触发同一业务键。

### BILL-002 生成前报价与扣点 — P0

- 创建页根据服务端配置显示预计消耗。
- 服务端以 `主体数量 × 1 点` 和价格版本计算最终消耗；3 个方案是每主体的固定交付组成，不允许前端篡改方案数降低价格。
- 提交时余额锁定、扣点、任务和账本在同一事务完成。
- 自 `0018_restore_generation_credit_debit.sql` 起，生产入口 `create_generation_job_v2` 已按上述规则真实扣点：每个主体 1 点，同一批多个主体按主体数一次扣除。
- 余额不足返回所需点数、当前余额和购买入口，设计草稿不得丢失。
- 系统为同一主体自动重试或补齐缺失方案不额外收费。
- 一个主体最终未完整交付 3 个方案时，整笔返还该主体的 1 点；可用的部分结果仍允许用户查看和下载。
- 失败方案重新生成不扣点，系统失败与质量补偿也不计费；同一方案通过幂等和活动任务锁避免重复提交。若未来增加次数上限，必须单独评审并同步价格页，不得静默扣点。
- 每个方案分别免费赠送 3 次细节调整，方案 1、2、3 各自独立计数；成功生成新图即消耗 1 次，平台侧失败不计次数，还原已有版本不调用模型也不计次数。
- 自动重试、扣点和返还均需要幂等业务键，不能因队列重复消费重复记账。
- 每个方案包含 3 次免费细节调整；第 4 次起每次消耗 1 点。付费调整通过 `create_variant_detail_edit_v2` 原子创建任务并扣点，失败通过 `refund_failed_variant_detail_edit_v2` 幂等返还；成功生成但未采用不退款。
- 购买点数和新用户赠送点数均永久有效；MVP 不实现点数到期、过期回收或按有效期排序扣点。

### BILL-002A 促销与优惠 — P1

- MVP 不向用户开放促销码输入框。
- 首发活动优先使用额外赠点，账本类型为 `promotion_bonus`，不直接修改已发布点数包价格。
- 促销赠点可以配置有效期；购买点数默认不失效。
- 后台赠点必须记录活动 ID、原因、操作人和幂等键。


1. 登录且已验证用户选择点数包。
2. 前端提交 `packageId` 和幂等键。

同一个支付 Session 或 Event ID 只能入账一次。

#### 内部订单与业务订单号

- 数据库 UUID `id` 是内部主键；另外由后端生成唯一、不可预测且适合客服沟通的 `order_number`，格式为 `ICO-YYYYMMDD-XXXXXXXXXX`。前端和导出文件展示业务订单号，不自行拼接或生成。
- `order_number` 使用安全随机字符并建立唯一索引；发生极低概率冲突时由后端重试。不得使用连续自增号码暴露订单量。

#### 账单摘要生成规则

- `billing-summary.json` 在导出时从订单和不可变点数账本计算，不作为余额或财务入账的权威数据源。
- 摘要包含统计起止时间、成功购买总额、退款总额、净支付额、购买点数、体验/促销赠点、生成消耗、失败返还、人工调整和当前余额。
- 所有金额使用整数最小货币单位并携带币种；首发只有 USD。若未来出现多币种，不允许直接跨币种相加。

### BILL-004 支付结果 `/billing/result` — P0

状态：确认中、成功、取消、失败、入账延迟。成功展示购买点数、新余额和返回创建页；入账延迟提供刷新但不重复创建订单。

### BILL-005 点数账本 `/account/credits` — P0

展示全部、消耗和充值三类记录。流水覆盖购买、CD-Key 充值、新用户赠送、生成扣点、失败/部分失败返还和管理员调整；每条包括类型、点数变化、余额快照、关联任务/订单、说明和时间。用户只能读取自己的记录，分页查询使用鉴权后的 `POST`，筛选条件不作为授权依据。

### BILL-005A CD-Key 充值 — P0

- 已登录且邮箱已验证、账户正常的用户，可在点数记录页输入 CD-Key 兑换点数。
- CD-Key 使用 `BAM-XXXX-XXXX-XXXX-XXXX` 展示格式，服务端忽略大小写和分隔符；前端校验只用于即时反馈，最终校验必须在数据库执行。
- 数据库只保存标准化兑换码的 SHA-256 哈希和末四位提示，不保存可再次使用的明文；明文只在运营创建时返回一次。
- 一枚 CD-Key 只能核销一次，可设置点数、到期时间、停用时间和内部备注。
- 锁定兑换码、检查有效性、增加余额和写入 `cd_key_redemption` 不可变账本必须在同一个数据库事务完成，防止并发重复到账。
- 普通用户不能读取兑换码表；运营端通过 Service Role 调用 `create_credit_redemption_code` 创建，密钥不得进入浏览器或日志。
- 当前运营命令：`npm run cd-key:create -- <点数> <ISO 到期时间或 -> [内部备注]`。

## 3. 最小运营支持模块

### 3.1 模块目标

首期建设轻量、受保护的 `/admin` 运营后台，覆盖数据总览、用户与任务只读排查、CD-Key 批次生成/停用和操作审计；不开放删除用户、直接改余额、删除账本等高风险能力。

### OPS-001 管理员保护 — P0

- 普通用户访问运营页面或 API 必须得到 403。
- 首版只区分管理员与普通用户，不建设多层 RBAC。
- 写操作必须填写原因、使用幂等键并写入不可变审计记录。

### OPS-002 用户与任务查询 — P0

- 通过 job ID 或用户邮箱查询生成任务、主体、3 个 variant、进度、错误码和扣点/返还摘要。
- 可按用户和任务状态查看余额、任务、进度与脱敏错误摘要。
- 第一阶段只读，不提供后台任务重试、复杂模型成本分析、灰度发布或设置管理。

### OPS-003 CD-Key 批次运营 — P0

- 管理员可按批次生成 CD-Key；明文仅返回一次，数据库只保存哈希。
- 批次可设置点数、数量、有效期、渠道和内部备注。
- 批次泄漏时可填写原因并停用全部未兑换码；创建和停用都必须进入不可变审计日志。
- 不提供直接修改余额、自动退款、争议工作台或完整用户管理。

### 3.2 API 与完成定义

已实现 API：`GET /api/admin/overview`、`POST /api/admin/users/query`、`POST /api/admin/jobs/query`、`POST /api/admin/audit/query`、`POST /api/admin/cd-keys/query`、`POST /api/admin/cd-keys/batches`、`POST /api/admin/cd-keys/batches/{batchId}/disable`。

完成定义：管理员可以查看核心运行状态、定位用户或生成问题，并安全生成/停用 CD-Key；普通用户不能访问；兑换码明文、密钥和完整内部 Prompt 不会从后台查询接口泄露。操作手册见[管理后台与 CD-Key 运营手册](../guides/admin-console-and-cd-key-operations.md)。
