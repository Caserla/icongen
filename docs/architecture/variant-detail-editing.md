# 方案细节调整与版本还原

## 产品行为

- 已完成的方案卡片提供“细节调整”入口，在弹窗中展示当前版本并输入 5–500 字的局部修改要求。
- 调整期间保留当前图片；生成完成后先展示草稿预览，只有用户点击“保存修改”才把它设为当前版本。
- 已调整方案支持“还原上一次修改”。还原沿父版本指针回退一级，不调用模型、不覆盖或删除历史资产；连续还原可逐步回到初始版本。

## Image2 调用

编辑请求只携带当前方案的 `sourceImage`（RGBA PNG），它是允许编辑的唯一图像输入。细节调整不重新发送风格参考板，避免模型把参考板主体或宫格内容带入结果；编译后的 style spec 继续约束配色、造型、材质、深度和细节密度。

提示词要求只应用用户指定的局部变化，并保持主体身份、构图、画布、视觉尺寸、线宽、配色、背景模式、背景形状、圆角和其他未指定细节。透明编辑优先请求原生 Alpha；供应商明确不支持透明编辑时，自动改用与原图主色距离最大的动态色键，随后清除与画布边界连通的临时背景、隐藏 RGB、色溢与低 Alpha 暗色污染。

带圆角或圆形背景的 App 插画图标以进入本次调整时的父版本 Alpha 为最终边界：Image2 只修改内部视觉内容，后处理逐像素替换为父版本 Alpha，而不是把新图 Alpha 与圆角蒙版相乘。这样首次生成的干净透明边界能够跨版本继承，且不会被编辑阶段产生的黑边、绿边或二次抗锯齿污染。方形背景与独立透明主体仍保留自身编辑轮廓，避免裁掉用户要求新增或改变的主体细节。

生成后执行质量检查，透明诊断与内容有效性采用不同策略：

- 透明输出仍检查真实 Alpha、四角和外围透明覆盖率、白底/黑底及假棋盘格，但 `FAKE_TRANSPARENCY_CHECKERBOARD`、`MISSING_ALPHA_CHANNEL`、`OPAQUE_TRANSPARENT_CANVAS_EDGE` 永久只记录告警，不触发质量重试，不阻止保存或进入双图确认页；
- 新图与原图会在忽略完全透明区的条件下进行低分辨率感知差异比较。只有抗锯齿、压缩或不可见像素变化时标记为 `EDIT_NO_VISIBLE_CHANGE` 并自动重试；三次仍无可见变化时明确失败，不进入双图确认页。

## 数据与资产

迁移 `0014_variant_detail_edits.sql` 新增：

- `generation_variant_revisions`：不可变的编辑版本、状态、指令和资产清单；
- `generation_variants.active_revision_id`：用户明确保存后的当前生效版本指针；
- 同一方案最多一个 `queued / processing` 编辑，防止重复提交。

Storage 路径：

```text
generated-icons/{jobId}/{subjectId}/variant-{slot}/revisions/{revisionId}/
  source.png
  preview.png
  {size}.png
  output.svg（仅支持的风格）
```

原始 `generation_assets` 永远不变。结果读取和 ZIP 下载在存在有效修订时使用修订资产，否则使用初始资产。

## 失败与并发安全

- 编辑失败只把修订标记为 `failed`，不改变原方案和任务状态。
- 还原会取消尚未完成的编辑，并把生效指针切换到当前版本的父版本。
- Worker 完成前再次确认修订仍为 `processing`；激活时同时核对父版本指针，避免过期 Worker 覆盖用户随后执行的还原或新编辑。
- Worker 每 20 秒实际等待并检查一次 Supabase 心跳写入；处理中租约为 5 分钟，覆盖最多 3 次 Image2 质量重试。心跳错误会记录日志，不再因为构造了未执行的惰性请求而误判任务中断。
- SVG 派生失败只记录日志，调整后的 PNG 仍可正常交付。

## 部署与验收

1. 在 Supabase 执行 `infra/supabase/migrations/0014_variant_detail_edits.sql`。
2. 部署 Worker 和 Web，确保 Worker 可读取同一套 Supabase 与 Image2 配置。
3. 对带背景、透明背景、交互线性图标各测试一次局部调整。
4. 验证页面更新、原图与尺寸 PNG 下载、可选 SVG、连续再次调整及还原初始版本。
5. 对圆角或圆形 App 图标比较父版本与新版本 Alpha 通道，必须逐像素一致；检查半透明边缘不存在黑色或色键残留。
